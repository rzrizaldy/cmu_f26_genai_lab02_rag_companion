Lab 02 · RAG: How does a machine read your resume?

Generative AI Lab · Fall 2026 · Friday 6 November 2026 · prepared by Rizaldy Utomo (TA)

We build a small retrieval-augmented generation (RAG) system over 424 real job postings, measure how well it works, and then use it on a resume. About 40 minutes, follow-along, three TODOs.

About this example. This may not reflect how HR teams or ATS software actually screen resumes. We use resumes because they are close to our daily life, so you can see how RAG works on something familiar.

Companion web app (same data, runs in your browser): https://rzrizaldy.github.io/cmu_f26_genai_lab02_rag_companion/

This guide is also online, so you can read it before anything is installed: https://rzrizaldy.github.io/cmu_f26_genai_lab02_rag_companion/readme/

Step 1: pick where to run it

A. Google Colab in the browser (easiest)

  1. Download lab02_starter.zip from Google Drive with your Andrew account, and unzip it. Keep the zip file too.
  2. Go to colab.research.google.com, choose File → Upload notebook, and pick lab02_rag.ipynb from the unzipped folder.
  3. Run the first code cell. It asks you to upload a file: pick the original lab02_starter.zip. A normal CPU runtime is enough; a GPU is not needed.
  4. Run the next cell (Connect Gemma). See Step 2 below.

We tested this on Colab on 3 Nov 2026 (free CPU runtime, torch 2.11, transformers 5.22). Everything up to Trial 4.5 ran in about 2.5 minutes, and Trial 4.5, where two small Gemma models run on the Colab CPU, adds about 2 minutes.

B. Your laptop with VS Code, Cursor or Jupyter

You need Python 3.10 or newer.

cd lab02_starter
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt    # about 2-3 minutes the first time (PyTorch)

Open lab02_rag.ipynb, choose the .venv kernel, and run the cells from the top. The first cell only checks that the files are there.

On Linux without a GPU you can save a 2 GB download by installing the CPU version of PyTorch first: pip install torch --index-url https://download.pytorch.org/whl/cpu.

C. VS Code connected to a Colab runtime (Colab extension)

The code runs there, but the extension can't mount Google Drive, and getting the zip onto the remote runtime is more fiddly than in the browser. Use A or B unless you already know this setup.

No Python at all?

Open the companion web app linked above. It runs the same chunking, embedding and matching in your browser, and you can try your own resume there.

Step 2: connect Gemma (the model that writes answers)

The lab uses two free Gemma models from Google:

Job Model Where it runs
turn text into numbers (embeddings) EmbeddingGemma, 300M on your machine or the Colab runtime, no key
write answers Gemma 4 (gemma-4-26b-a4b-it) Gemini API, needs a key

When you run the Connect Gemma cell, a hidden box asks for a key. Pick one:

Option What to do Notes
1. Your own free key (recommended) aistudio.google.com/apikey → Create API key, in a new project without billing. Paste it into the box. Gemma has no paid tier on the Gemini API, so it cannot be billed. To skip the box next time, save it as GEMINI_API_KEY in Colab Secrets (key icon on the left) or in .env.
2. The shared class key Just press Enter in the box. Already inside this zip. At most 40 calls per session, slow when 40 people use it at once, and deleted on Fri 13 Nov 2026.
3. No key: Gemma inside the notebook Replace rk.llm.setup() with rk.llm.setup("local"). Runs Gemma 3 1B on your machine or Colab (about 2 GB download once). Free and private, but the answers are clearly weaker. On a free Colab CPU each answer takes about a minute, so switch to a GPU first (Runtime → Change runtime type → T4 GPU).
4. No key: Gemma with Ollama Install Ollama, run ollama pull gemma3:4b, then use rk.llm.setup("ollama"). Laptop only. Better answers than option 3, but a 3 GB download.
5. Nothing works Do nothing. Every Gemma cell shows the answer from the TA's run, marked "saved answer". Everything else in the lab still works.

Never paste a key into a code cell, and never upload .env anywhere.

Trying your own resume

Keep in mind that this score only shows how close the text of your resume is to the text of a posting. It may not reflect how HR teams or ATS software actually screen resumes.

At the end of step 6 the notebook can match your own resume against the 424 postings. You can give it a PDF in two ways on Colab: drag the file into the Files pane (the folder icon on the left) and write its name in MY_RESUME_FILE, or mount your Google Drive and write the full path, such as /content/drive/MyDrive/my_resume.pdf. On a laptop, put the PDF in the lab02_starter folder. You can also paste the text instead. The matching runs inside the notebook, so the resume is not sent to Gemma. If you'd rather keep it off Colab entirely, the companion app reads the PDF inside your browser.

Questions from lecture: designing the vector store

Section 7 of the notebook answers three questions students asked in lecture, using our own postings. The companion app has the same answers inside steps 2 and 3, and the FAQ has the details. It takes a few minutes and at most two Gemma calls.

Question Short answer What we measured
What information should we embed? Text that people describe in words, with enough context to stand on its own. Keep exact facts like dates, places and salary as fields you can filter on. MRR on the 48 test questions: chunk with job title and section 0.93, whole posting as one vector 0.80, job title alone 0.49
If an LLM generates a response, can we store it? Yes, as a semantic cache. Embed the question, keep the answer beside it, label it as generated, and keep it apart from the source documents. A saved wrong answer ranked first (0.81) above the best real posting (0.55) for a later question
How do time and place fit in? Store them as fields and check them with plain code before reusing an answer. An answer should expire when its first source does. "Remote" vs "on-site" questions score 0.92, above two real paraphrases. Search alone found 0 of 10 chunks in the right state for a Texas question, and a filter found 10 of 10.

These results come from our small dataset and from 13 question pairs written by hand, so please test on your own data before relying on any of them.

Optional: the Gemma copy in the class Google Drive

Troubleshooting

What you see What to do
429 or "rate-limited" The shared key is busy. Wait 30 seconds, or use your own key.
402 or "prepayment credits depleted" Your key's project has billing attached. Make a new key in a new project without billing.
"you reached the 40-call limit" Restart the runtime and run the first cells again. With your own key on a laptop you can set LAB_MAX_CALLS=200 in .env.
"waiting for EmbeddingGemma to finish downloading" Normal in the first minute after the setup cell. The cell continues by itself.
Run this notebook from inside lab02_starter/ Colab: run the first cell again. Laptop: open the notebook from inside the unzipped folder.
Colab renamed the zip to lab02_starter (1).zip That's fine; the first cell still finds it.
A TODO 1 setting takes minutes You picked a setting that is not in the list in the comment, so about 4,000 chunks are being embedded. Pick a listed setting.
"Your zip is older than this notebook" in section 7 Download the newest lab02_starter.zip from Google Drive. On Colab, choose Runtime → Disconnect and delete runtime, then start again from the first cell.
Can't find my_resume.pdf Check the exact file name in the Files pane, including capital letters. For a file in Google Drive, run the drive.mount line first and use the full path.
"That is very little text" after reading a PDF The PDF is probably a scanned image with no text inside. Paste the text into MY_RESUME instead, or use the companion app.
Companion says "bundle not found" You opened your own companion/index.html before running the export cell in step 6. Use the hosted link instead.
